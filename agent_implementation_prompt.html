Prompt de Implementacao para Agente de IA

Objetivo: implementar, com testes, as melhorias combinadas para o BDR: usar nome civil como identificacao principal dos deputados quando houver, corrigir o filtro de partidos no dashboard para nao exibir siglas historicas indevidas, e revisar o fluxo do ETL para reduzir acoplamento sem remover a normalizacao necessaria.

Contexto funcional

Este repositorio contem um pipeline ETL em Python, um schema PostgreSQL, consultas SQL exportadas como respostas e um dashboard com backend FastAPI e frontend React/Vite. O problema atual tem tres frentes principais:

  • A consulta Q1 hoje usa apenas nome, mas ha casos de homonimos. O campo nome_civil existe e deve ser preferido para exibição quando presente.
  • O filtro de partidos no dashboard mostra siglas historicas ou inconsistentes, como ARENA, porque a lista de filtros e derivada de dados de resposta e/ou inventarios nao canonicos.
  • O ETL faz leitura, limpeza, enriquecimento e carga direta via COPY. A ideia e reduzir ambiguidade e acoplamento, mas sem remover a etapa de normalizacao que garante consistencia dos dados.

Escopo da implementacao

O agente deve implementar as mudancas a seguir de forma incremental, preservando compatibilidade sempre que possivel.

  1. Q1 deve exibir nome civil como label principal, com fallback para nome parlamentar apenas quando nome civil estiver vazio ou nulo.
  2. O dashboard deve parar de depender de uma lista historica implícita de partidos e passar a consumir um catalogo canonico.
  3. Partidos historicos ou descontinuados nao devem aparecer como opcoes “ativas” sem classificacao explicita.
  4. O ETL deve ser reestruturado para separar claramente extracao, padronizacao e carga, mantendo integracao com a API oficial da Camara.
  5. Adicionar testes para a Q1, para o filtro de partidos e para o comportamento do ETL/contratos impactados.

Arquivos e areas provaveis de impacto

  • Banco/init.sql e Banco/docker-compose.yml se houver necessidade de corrigir o ponto de entrada do schema do PostgreSQL.
  • Caio/consultas/q1.sql para alterar a saida da Q1.
  • dashboard/backend/app/question_registry.json para alinhar colunas esperadas e rotulos da Q1.
  • dashboard/backend/app/service.py, dashboard/backend/app/filter_engine.py, dashboard/backend/app/models.py e possivelmente dashboard/backend/app/adapters/base.py para a origem e aplicacao de filtros.
  • dashboard/frontend/src/components/GlobalFilters.tsx e tipos relacionados para refletir o catalogo canonico sem inferencia local.
  • src/loaders.py, src/mappings.py, src/db.py e docs/md's/ETL.md para a reorganizacao do ETL.
  • Arquivos de testes em dashboard/backend/tests e dashboard/frontend/src/**/__tests__.

Diretrizes tecnicas obrigatorias

  • Preservar compatibilidade de contrato sempre que possivel. Se um campo antigo precisar ser removido, atualizar o consumidor no mesmo lote de mudancas.
  • Evitar refatoracoes amplas sem teste. Cada alteracao deve ser pequena, localizada e validada.
  • Manter o ETL com uma etapa de limpeza/normalizacao; nao eliminar a transformacao apenas para simplificar o pipeline.
  • Se for introduzida uma camada staging em JSON ou JSONB, ela deve ficar claramente separada da carga analitica final.
  • Para partidos, diferenciar claramente entre partido atual, partido historico e sigla invalida/legada.
  • Quando houver homonimos, o nome exibido deve favorecer nome_civil e nao o nome parlamentar, salvo ausencia de dado.
  • Se o filtro de partidos continuar baseado em strings, normalizar siglas com a mesma logica ja usada no ETL e no backend.

Plano de implementacao sugerido

  1. Corrigir a Q1
    • Alterar a query para selecionar nome_civil como label principal, com fallback para nome.
    • Garantir que o arquivo exportado continue compatível com o dashboard ou ajustar o registry e o front no mesmo passo.
    • Revalidar a ordenacao e o schema da saida.
  2. Definir catalogo canonico de partidos
    • Criar uma fonte de verdade para partidos usados no front e no backend.
    • Adicionar status para siglas historicas ou descontinuadas.
    • Atualizar a coleta do catalogo de filtros para nao depender apenas das respostas exportadas.
  3. Ajustar dashboard e contratos
    • Revisar question_registry.json para refletir as colunas corretas.
    • Ajustar componentes de filtro e qualquer renderer que assuma nome como label primario.
    • Se necessario, expor um campo adicional para rotulo amigavel e um campo separado para identificacao canonica.
  4. Reestruturar o ETL
    • Mapear entradas brutas, saidas padronizadas e carga final.
    • Evitar que o parser fique espalhado por multiplos locais sem contrato.
    • Manter enriquecimento via API oficial e validar campos criticos como cpf, nome_civil e escolaridade.
    • Se houver staging em JSON, documentar claramente sua responsabilidade e nao substituir a validacao principal sem teste.
  5. Atualizar documentacao
    • Documentar a nova regra de nome civil.
    • Documentar a politica de partidos ativos, historicos e descontinuados.
    • Descrever o novo fluxo do ETL e os formatos intermediarios, se existirem.

Requisitos especificos para a Q1

  • Usar nome_civil como o valor exibido nas respostas quando houver dado valido.
  • Se nome_civil estiver ausente, usar nome como fallback.
  • Preservar id_deputado, sigla_uf, sigla_partido e gasto_total.
  • Nao quebrar a exportacao para /respostas/q1_gastos_deputados.txt.
  • Se o dashboard usar o nome como label do grafico, ajustar o contrato correspondente.

Requisitos especificos para partidos

  • Remover siglas historicas do conjunto padrao de filtros quando elas nao fizerem parte do conjunto canonico ativo.
  • Se for necessario manter siglas historicas por analise temporal, exibir o status do partido de forma explicita.
  • Evitar que o front construa a lista de partidos a partir de arquivos de resposta sem uma camada de validacao.
  • Garantir que siglas como ARENA nao aparecam como partido ativo se forem apenas legado historico.

Requisitos especificos para o ETL

  • Manter o enriquecimento via API da Camara para preencher dados complementares.
  • Preservar limpeza, normalizacao e validacao de tipos.
  • Se o novo desenho usar JSON, criar uma separacao clara entre raw, staging e analitico.
  • Nao remover a etapa de verificacao de chaves, obrigatoriedade e duplicatas sem substituicao equivalente.
  • Garantir que a carga final continue consistindo no schema PostgreSQL.

Testes obrigatorios

O agente deve falhar a tarefa se nao conseguir provar as mudancas com testes executaveis.
  1. Teste da Q1
    • Validar que a exportacao contem nome civil quando disponivel.
    • Validar fallback para nome parlamentar quando nome civil faltar.
    • Validar que a ordenacao por gasto total segue correta.
  2. Teste do filtro de partidos
    • Verificar que partidos historicos nao entram como ativos por acidente.
    • Verificar que o front recebe apenas partidos validados pelo backend.
    • Verificar que a busca por sigla continua funcionando apos a mudanca.
  3. Teste do ETL
    • Validar que a carga continua gerando as tabelas e saidas padronizadas.
    • Validar que os campos criticos continuam preenchidos e com tipos esperados.
    • Se houver staging JSON, validar round-trip ou conversao equivalente.
  4. Teste de integracao do dashboard
    • Validar que a pagina de Q1 carrega com o novo nome sem quebrar colunas ou graficos.
    • Validar que o painel nao mostra opcoes indevidas de partidos.

Comandos de validacao esperados

O agente deve executar os testes adequados ao stack alterado. Exemplos do que se espera observar:

  • Backend Python: testes com pytest ou equivalente do pacote.
  • Frontend React: testes do projeto com npm test, npm run test ou vitest, conforme configuracao existente.
  • ETL Python: validacao do pipeline com execucao controlada e verificacao do artefato gerado.
  • Se alterado o schema: validação com subida do banco e verificação da consulta Q1.

Critérios de aceite

Considerar a tarefa concluida somente se todos os itens abaixo forem verdadeiros.
  • A Q1 exibe nome civil como identificacao principal sem perder compatibilidade operacional.
  • O filtro de partidos nao exibe siglas historicas como opcoes ativas indevidas.
  • O ETL continua carregando corretamente no PostgreSQL com normalizacao e enriquecimento preservados.
  • O dashboard carrega sem erro nas rotas impactadas.
  • Os testes relevantes passam e foram executados apos as mudancas.

Instrucoes finais ao agente

1. Leia os arquivos afetados antes de editar.
2. Faça mudancas pequenas e localizadas.
3. Nao remova contratos existentes sem atualizar os consumidores no mesmo lote.
4. Exija testes e execute-os.
5. Se houver ambiguidade sobre partidos historicos, prefira adicionar status explicito em vez de apagar dados.
6. Se houver homonimos, prefira nome_civil como label de exibicao.
7. Entregue um resumo final com arquivos alterados, comportamento mudado e evidencias de teste.
